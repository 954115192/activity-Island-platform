# Activity Island 产品演进与架构改造方案

> 文档状态：方案初稿
>
> 目标版本：从“插件驱动的 Windows 灵动岛”演进为“电脑与手机之间的轻量信息与操作入口”

## 1. 先做出的产品决策

Activity Island 继续保留插件体系，但不再坚持“所有功能都必须由插件提供”。

后续采用四层模型：

```text
灵动岛表现层
  └─ 小岛窗口、三态布局、动画、提醒仲裁、主题、交互

平台基础能力层
  └─ Windows 通知、设备配对、连接会话、文件传输、权限、事件路由、存储

官方功能模块层
  └─ 通知中心、手机桥、文件互传、设备中心、剪贴板同步等完整用户功能

第三方扩展层
  └─ 用户自定义插件、外部服务接入、自动化规则、个人工作流
```

判断标准只有一条：

> 多个功能共同依赖的机制属于平台；需要对普通用户开箱即用的完整体验属于官方模块；因用户而异的功能属于插件。

这意味着插件仍然是产品的重要能力，但它从“产品的唯一承载方式”变成“建立在平台能力之上的扩展方式”。

## 2. 当前产品定位

### 2.1 当前产品是什么

当前产品是一个 Windows 桌面灵动岛 Host：

- Electron 宿主负责窗口、外壳、裁剪、三态尺寸、动画、提醒和展开仲裁。
- 插件是独立网页，负责自己的业务逻辑、内容和三态界面。
- 插件通过契约化 SDK 与宿主通信。
- 后台脚本负责读取本机数据或联网，并以事件形式推给插件。
- 控制台负责插件安装、启停、排序、参数和日志。
- 工作台是宿主自己的全屏任务面板，与插件是两种不同的产品形态。

目前的产品主张可以概括为：

> 一个不打扰桌面、可以自由安装功能的 Windows 信息入口。

### 2.2 当前路线的优点

现有插件路线已经解决了几个很难的问题：

1. 宿主和业务解耦，插件可以独立开发和热重载。
2. Small、Medium、Large 三态统一，功能能自然适配灵动岛。
3. Alert、Focus、Ambient 已经有统一的显示仲裁。
4. 插件可以通过后台脚本接入本机数据和网络。
5. 用户可以安装自定义功能，未来也容易接入 AI 生成插件。

这些能力应该保留，不能因为增加手机桥梁就推倒重来。

### 2.3 当前路线的边界

“每个功能都是插件”在小功能阶段很有效，但在下面几类功能上会产生结构性问题：

- Windows 通知监听需要系统授权、去重、历史、应用来源和生命周期管理。
- 手机连接需要配对、认证、加密、重连和设备状态管理。
- 文件互传需要统一的传输会话、分片、校验、暂停、恢复和进度。
- 剪贴板同步需要冲突策略、隐私开关和内容大小限制。
- 多个插件如果各自连接手机，会重复配对、抢占连接并产生权限失控。

这些不是某个插件的业务逻辑，而是多个功能共同依赖的平台机制。继续让插件自行实现，会让插件之间互相重复、互相竞争，最后形成一个难以维护的“插件总线操作系统”。

## 3. 目标产品定位

### 3.1 新定位

目标产品不是一个“插件展示器”，也不是一个完整的手机管家，而是：

> **Activity Island 是 Windows 桌面上一个低打扰的信息入口和设备桥梁：把重要通知、手机状态、跨设备任务和用户自定义操作，统一呈现在一个可扩展的灵动岛中。**

它包含三种价值：

- **看见**：不打开大窗口就能看到电脑和手机的重要状态。
- **处理**：在岛上完成确认、暂停、回复、发送、打开等轻操作。
- **连接**：让手机和电脑之间的通知、文件和剪贴板可以自然流动。

### 3.2 产品边界

Activity Island 应该专注于“轻量、即时、跨设备”的信息与操作：

- 适合：通知、传输进度、设备状态、媒体状态、任务结果、快捷动作。
- 不适合：完整聊天、复杂文件管理、照片编辑、长时间表格操作、重型工作流。

复杂任务交给工作台或系统原生应用；灵动岛负责把用户带到正确的位置，并承接短操作。

### 3.3 对用户的最终描述

用户安装后应该得到一个可以直接使用的基础产品：

1. Windows 通知可以在岛上显示。
2. 可以扫码配对 Android 手机。
3. 可以在电脑和手机之间发送文件。
4. 可以根据需要安装插件，扩展外部服务和个人自动化。

普通用户不需要先理解插件、后台脚本或能力声明，才能使用核心功能。插件和工作台是扩展能力，而不是使用产品的前置条件。

## 4. 目标架构

### 4.1 灵动岛表现层

继续由现有 Host 负责：

- Island Window、透明窗口、命中检测和托盘。
- Small / Medium / Large / Custom 状态。
- 布局、缩放、裁剪、主题和动画。
- Ambient、Alert、Focus 的优先级与队列。
- 用户操作优先、勿扰和全屏策略。
- 所有模块和插件的统一视图生命周期。

这一层不直接实现通知同步或文件传输业务，只负责“怎么显示”和“用户当前在操作什么”。

### 4.2 平台基础能力层

平台层负责共享机制，并以受控 API 对上提供能力。

建议拆成以下服务：

| 服务 | 职责 | 第一版范围 |
|---|---|---|
| `NotificationService` | 读取、标准化、去重、存储和分发通知 | Windows 通知监听、应用过滤、历史、跳转 |
| `DeviceService` | 设备发现、配对、认证、连接和状态 | 局域网扫码配对、设备列表、心跳、重连 |
| `TransferService` | 文件传输会话、进度、校验和恢复 | 单文件/多文件发送、暂停、取消、完成通知 |
| `ClipboardService` | 跨设备剪贴板同步 | 第二阶段以后，默认关闭 |
| `PermissionService` | 能力授权、用户确认和撤销 | 按模块/插件/设备记录授权 |
| `EventRouter` | 按权限和订阅分发领域事件 | 替换无边界的全量广播 |
| `PlatformStorage` | 设备、授权、通知历史和传输记录 | 加密敏感配置，限制保留周期 |

这些服务可以先放在 Electron 主进程的独立模块中，后续把设备连接和传输下沉为独立子进程。服务之间使用明确的接口，不让 UI 或插件直接管理 socket、文件流和系统句柄。

### 4.3 官方功能模块层

官方模块是产品直接承诺的功能，随安装包提供或由宿主管理。它们可以复用插件的三态视图机制，但拥有比普通插件更稳定的生命周期和平台 API。

第一批建议包含：

1. **Windows 通知中心**：实时提醒、最近历史、应用过滤、点击跳转。
2. **手机桥**：设备配对、在线状态、电量、连接设置和授权管理。
3. **文件互传**：选择设备、发送/接收确认、进度、暂停、失败重试和打开目录。
4. **设备中心**：管理已配对设备、权限、连接方式和默认设备。

后续再增加：

- 剪贴板同步。
- 手机电量和网络状态。
- 电脑媒体控制在手机端的镜像。
- 通知规则和自动化中心。

官方模块的共同特征是：平台能力由宿主管理，用户体验由模块负责，失败时不影响灵动岛本身。

### 4.4 第三方插件层

插件继续适合以下功能：

- 番茄钟、倒计时、系统指标、媒体控制。
- Git、CI、天气、余额、项目状态等外部服务。
- 用户自己的 HTTP、脚本和数据源。
- 个人自动化规则，例如特定通知出现时提醒、记录或调用服务。
- 对官方平台能力的轻量调用，例如“把当前文件发送到默认手机”。

插件不应直接获得以下底层权限：

- 任意读取所有系统通知。
- 任意读取所有手机数据。
- 直接管理设备连接和配对密钥。
- 绕过平台传输服务读写任意传输会话。
- 默认向其他插件广播通知正文或文件内容。

插件可以申请受限能力，平台负责授权、审计和撤销。

### 4.5 工作台层

工作台保留为“复杂任务面板”：

- 文件队列和传输历史。
- 通知搜索、筛选和批量处理。
- 设备管理和规则编辑。
- 复杂的插件/模块配置。

灵动岛负责即时反馈，工作台负责密集操作。两者不要互相替代。

## 5. 功能归属表

| 功能 | 归属 | 原因 |
|---|---|---|
| 小岛窗口、动画、裁剪、三态布局 | 宿主核心 | 所有内容共享，必须统一视觉和生命周期 |
| Alert / Focus / Ambient 仲裁 | 宿主核心 | 需要全局优先级和用户操作优先 |
| 插件安装、启停、排序、日志 | 插件平台 | 是扩展系统的公共管理能力 |
| Windows 通知监听 | 平台服务 | 需要系统权限、去重、历史和统一生命周期 |
| Windows 通知展示 | 官方通知模块 | 是用户直接使用的完整体验 |
| 手机发现、配对、加密连接 | 平台服务 | 所有手机功能共享，不能由各插件重复实现 |
| 文件传输协议和会话 | 平台服务 | 需要统一可靠性、校验、恢复和权限 |
| 文件发送/接收界面 | 官方文件模块 | 用户需要开箱即用的完整流程 |
| 剪贴板同步 | 平台服务 + 官方模块 | 涉及隐私、冲突和大小限制 |
| 番茄钟、天气、余额、项目状态 | 第三方插件 | 业务差异大，适合独立开发和替换 |
| 自定义通知规则 | 插件/规则模块 | 规则因人而异，但只能使用平台授权事件 |
| 设备管理、授权、历史搜索 | 工作台/官方模块 | 操作密集，不适合长期占据小岛 |

## 6. 插件契约的改造方向

当前契约继续作为 UI 和生命周期基础，下一版重点增加能力模型和事件订阅模型。

### 6.1 从“能调用”改成“声明后才能调用”

插件清单增加能力声明，示意如下：

```json
{
  "contract": 3,
  "capabilities": [
    "notifications.subscribe:metadata",
    "devices.list",
    "transfers.create"
  ],
  "subscriptions": [
    "transfer.updated"
  ]
}
```

能力必须分级，不能只提供一个过宽的 `notify` 或 `device`：

- `notifications.subscribe:metadata`：只收到应用名、标题和时间。
- `notifications.subscribe:content`：收到正文，需要单独确认。
- `devices.list`：只能看到已授权设备的基本信息。
- `transfers.create`：可以创建发送任务，但不能读取其他插件的传输内容。

### 6.2 事件路由改造

现有事件模型适合插件内部事件和低敏感状态。接入真实通知和手机数据后，改为领域事件：

```text
NotificationService ──▶ EventRouter ──▶ 官方通知模块
                                      ├─▶ 已授权插件
                                      └─▶ 规则引擎

TransferService ──────▶ EventRouter ──▶ 文件互传模块
                                      └─▶ 订阅 transfer.updated 的插件
```

事件路由必须做到：

- 默认不广播敏感数据。
- 插件只能收到自己声明并获批的事件。
- 通知正文、文件名、路径分别控制权限。
- 事件带 `source`、`eventId`、`timestamp` 和 `sensitivity`。
- 统一处理去重、过期和取消订阅。

### 6.3 API 形态

插件只使用平台 API，不直接接触底层实现：

```ts
await island.notifications.subscribe({ scope: 'metadata' })
await island.devices.list()
await island.transfers.create({ deviceId, files })
island.events.on('transfer.updated', handler)
```

每个调用都应返回结构化结果，例如 `ok`、`error`、`requestId` 和实际权限范围，避免把平台错误直接抛到插件页面。

## 7. 分阶段改造计划

### 阶段 0：边界冻结与基线整理

目标：不增加新功能，先把边界定下来。

工作内容：

1. 把“宿主核心、平台服务、官方模块、插件、工作台”写成代码目录和文档中的固定概念。
2. 把现有通用事件分为 UI 事件、插件事件、平台领域事件。
3. 为通知、设备、传输预留接口和错误模型，暂不接入真实设备。
4. 固化数据目录、日志格式、版本兼容策略和故障恢复方式。
5. 保留当前插件契约 v2，新增 v3 草案，旧插件继续运行。

完成标志：新增功能不会再直接往 `main.ts` 堆业务逻辑，也不会把平台能力伪装成普通插件后台脚本。

### 阶段 1：平台服务骨架与官方模块入口

目标：让“官方模块”和“第三方插件”在结构上分开。

工作内容：

- 新增 `electron/platform/`，放能力、权限、事件路由和存储接口。
- 新增 `electron/notifications/`、`electron/devices/`、`electron/transfers/` 的空实现和单元测试。
- 新增 `console-apps/modules/` 或等效目录，放官方功能模块。
- 控制台增加“官方功能”和“第三方插件”两个分区。
- 能力授权页面先支持查看、确认和撤销。

完成标志：官方模块可以使用平台接口，普通插件不能绕过接口访问同一资源。

### 阶段 2：Windows 通知 MVP

目标：先证明 Activity Island 能成为电脑通知入口。

第一版范围：

- 读取 Windows 通知并标准化为统一事件。
- 应用名、图标、标题、正文摘要、时间和跳转目标。
- 应用白名单/黑名单。
- 去重和短期历史。
- 通过 Alert 显示新通知，点击后在 Medium 查看，必要时跳转来源应用。
- 设置中提供启用、暂停和清空历史。

暂不做：

- 代替所有系统通知按钮。
- 跨设备通知同步。
- 对所有通知正文做永久保存。

完成标志：真实通知稳定进入岛上，重启、休眠、全屏和插件重载后不会重复刷屏或丢失宿主状态。

### 阶段 3：设备桥与文件互传 MVP

目标：先打通电脑与手机的可靠连接，再做通知同步。

第一版建议优先支持 Windows + Android：

1. 电脑生成一次性配对二维码。
2. Android App 扫码并完成密钥交换。
3. 设备服务显示在线/离线、名称和最后连接时间。
4. 电脑向手机发送文件。
5. 手机向电脑发送文件。
6. 岛上显示等待确认、传输中、完成、失败和重试。
7. 工作台显示传输队列和历史。

传输层需要一开始就设计：文件大小、分片、哈希校验、取消、断线重连、临时文件清理和目标目录选择。先做局域网，不在第一版承诺公网中继。

### 阶段 4：Android 通知同步与规则

目标：让手机通知成为第二个可靠信息源。

工作内容：

- Android 端通过系统授权读取通知。
- 手机端先过滤应用，再发送到电脑。
- 电脑端再次按设备和应用策略过滤。
- 为通知生成设备维度的唯一 ID，避免电脑和手机重复提醒。
- 支持静音、仅显示标题、仅显示重要应用等策略。
- 将通知订阅能力开放给官方规则模块和经过授权的插件。

第一版不承诺 iPhone 具备同等的第三方通知读取能力。iPhone 可以先作为文件传输设备接入，通知能力待平台许可和实际可行性验证后单独评估。

### 阶段 5：开放平台与生态

目标：让平台能力真正服务于插件生态，而不是只服务官方模块。

- 发布插件契约 v3 和能力 SDK。
- 提供通知、设备、传输的模拟器，插件不依赖真实手机也能开发。
- 提供权限说明、事件样例和故障诊断工具。
- 增加插件导入时的能力审查和风险提示。
- 后续再考虑签名、可信作者、插件市场和远程更新。

## 8. 版本与任务优先级

建议用下面的产品版本组织改造：

| 版本 | 重点 | 用户能感知到的结果 |
|---|---|---|
| `0.3` | 平台分层、官方模块入口、契约 v3 草案 | 结构稳定，现有插件不受影响 |
| `0.4` | Windows 通知中心 | 电脑通知可在岛上查看和处理 |
| `0.5` | 设备配对与文件互传 | 手机和电脑可以双向传文件 |
| `0.6` | Android 通知同步 | 手机通知可以在电脑岛上看到 |
| `0.7` | 规则、剪贴板和授权完善 | 设备桥成为可配置平台 |
| `1.0` | 稳定性、权限、升级和生态 | 核心功能可长期使用，插件可持续扩展 |

优先级排序：

1. 平台边界和事件权限。
2. Windows 通知闭环。
3. 局域网配对和文件互传。
4. Android 通知同步。
5. 剪贴板和自动化。
6. 市场、签名和分发。

不要先做插件市场、复杂自动化或公网传输。基础连接不稳定时，扩展越多，问题越难定位。

## 9. 建议的代码组织

最终目录可以逐步靠近下面的形态：

```text
electron/
  host/                 # 窗口、布局、动画、仲裁、生命周期
  platform/
    capabilities/       # 能力声明、授权、撤销
    events/             # 领域事件、订阅、路由
    storage/            # 平台数据和保留策略
    notifications/      # Windows 通知适配
    devices/            # 配对、连接、设备状态
    transfers/          # 文件传输会话和协议
  plugins/              # 第三方插件安装、视图、后台脚本和 v2/v3 兼容
  modules/              # 官方通知、手机桥、文件互传等模块
  workbench/            # 复杂任务面板
  preload/

console-apps/
  modules/              # 官方模块页面
  workbench/            # 工作台页面

packages/
  plugin-sdk/           # UI SDK + 平台能力 SDK
  platform-types/       # 事件、能力、设备、传输公共类型
```

这不是要求一次性重命名所有文件，而是后续新增代码的落点。现有 `main.ts` 中的业务逻辑应按功能逐步迁出，避免一次大重构造成回归风险。

## 10. 稳定性和安全原则

### 权限

- 默认最小权限；插件没有声明就没有能力。
- 通知正文、手机数据和文件内容属于敏感数据，单独授权。
- 用户可以按插件、按设备撤销权限。
- 平台 API 不返回原始连接凭据和配对密钥。

### 稳定性

- 设备服务、传输服务和通知监听必须可独立重启。
- 传输失败不能让岛窗口或插件视图崩溃。
- 所有领域事件带唯一 ID，消费端可以幂等处理。
- 重启后恢复未完成传输的状态，但不重复触发已经确认的提醒。
- 通知历史和临时文件都要有保留上限和清理任务。

### 兼容性

- 插件契约采用新增字段、保留旧字段的方式升级。
- v2 插件继续运行，不能因为平台服务上线而强制迁移。
- 官方模块可以使用更高版本的内部 API，但对外平台 API 必须有稳定版本。

## 11. 需要明确的非目标

为了避免产品失控，以下内容暂不纳入第一阶段：

- 不做完整手机桌面投屏。
- 不做完整聊天客户端。
- 不做公网文件中继和云盘替代品。
- 不让插件默认获得全量系统通知或手机数据。
- 不为了“生态”过早实现在线插件市场。
- 不把所有设置、历史和复杂任务塞进小岛。

## 12. 判断改造是否成功

第一阶段可以用以下指标验证，而不只看功能数量：

- 用户安装后不需要先装插件就能看到核心通知功能。
- Windows 通知从到达到岛上提醒的延迟稳定在可接受范围内。
- 通知去重、全屏、勿扰、休眠和重启场景没有明显重复或丢失。
- 手机配对过程可以在一分钟内完成，断线后能自动恢复。
- 文件传输有明确进度、失败原因和重试入口。
- 旧版插件继续可用，新插件可以用能力声明调用平台服务。
- 一个平台连接只维护一份，多个官方模块和插件可以共享，而不会各自重复配对。

## 13. 最终产品结构

最终可以用一句话描述各部分关系：

```text
灵动岛负责“呈现和打断”
平台负责“连接和保护”
官方模块负责“开箱即用”
插件负责“自由扩展”
工作台负责“复杂操作”
```

这条路线既保留了当前项目最有价值的插件能力，也解决了通知同步、手机桥梁和文件传输不适合由插件各自实现的问题。产品不再是“插件的集合”，而是一个有核心能力、有官方体验、又允许用户继续扩展的平台。
