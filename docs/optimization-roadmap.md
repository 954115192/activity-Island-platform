# Activity Island 优化与扩展建议

> 基于代码审查与架构分析 · 2026-10-31

## 当前项目状态

**已完成的核心能力：**
- ✅ 灵动岛窗口与三态布局（Small/Medium/Large）
- ✅ 插件系统与生命周期管理
- ✅ Windows 通知监听与历史记录
- ✅ 本地端口通知接口（`127.0.0.1:5720`）
- ✅ LocalSend 兼容的文件传输
- ✅ 工作台界面框架
- ✅ 验证码识别与一键复制
- ✅ 通知等级分类（info/warn/critical）与颜色标识

**架构特点：**
- 平台服务已初步分层（`packages/platform-services`、`packages/platform-contracts`）
- 插件契约 v2 运行稳定，v3 草案已在演进计划中
- 测试覆盖包含契约测试、集成测试和 E2E 测试
- 代码已按功能域拆分（`electron/notifications`、`electron/transfers`、`electron/plugins` 等）

## 一、紧急改进项（技术债与稳定性）

### 1. main.ts 过度集中

**现状：** `apps/desktop/electron/main.ts` 有 3377 行，101 个 ipcMain 处理器，134 个函数定义，承担了太多职责。

**影响：** 新功能难以定位落点，错误传播范围大，测试困难。

**建议：**
按领域拆分到独立模块，保留 `main.ts` 只做启动、生命周期协调和顶层错误处理。可以逐步迁移：
- 通知相关 IPC → `electron/notifications/ipc-handlers.ts`
- 传输相关 IPC → `electron/transfers/ipc-handlers.ts`
- 插件管理 IPC → `electron/plugins/ipc-handlers.ts`
- 窗口与岛状态 IPC → `electron/island/ipc-handlers.ts`

每个模块暴露一个 `registerHandlers(ipcMain)` 函数供 main.ts 调用。

**优先级：** 高（影响后续所有功能开发）

---

### 2. 代码重复：policy.ts 和 service.ts 的两份副本

**现状：** `packages/platform-services/src/notification/` 和 `apps/desktop/electron/notifications/` 下有几乎相同的文件（policy.ts、service.ts、history.ts 等），只有细微注释差异。

**影响：** 修改时容易只改一处，导致行为不一致；测试需要覆盖两遍。

**建议：**
- 确定 `packages/platform-services` 为权威实现
- `apps/desktop/electron` 只保留 Electron 特有的适配层（如 Windows 通知源、IPC 绑定）
- 业务逻辑、策略判断、历史存储全部依赖 platform-services 包

**优先级：** 高（技术债，影响维护效率）

---

### 3. 无障碍与减少动态支持不足

**现状：** 检索 `prefers-reduced-motion`、`aria-*` 和 `a11y` 相关代码，只在少数地方有 `aria-label` 和 `aria-hidden`，没有系统性处理。

**影响：** 不符合 DESIGN.md 第 4 节承诺的无障碍标准，用户开启减少动画后体验可能仍有大幅动效。

**建议：**
- 在 CSS 中增加 `@media (prefers-reduced-motion: reduce)` 规则，禁用非必要的 transition 和 animation
- 为所有交互元素补全 `aria-label`、`role` 和键盘焦点顺序
- 在 E2E 测试中增加一个"减少动态效果"场景，确保岛仍可正常使用

**优先级：** 中（产品质量，1.0 前必须完成）

---

### 4. 端口通知接口缺少速率限制实际生效验证

**现状：** `local-trigger.ts` 有 `rateLimitPerMinute` 配置（默认 120），但没有找到对应的集成测试验证超限后的行为。

**风险：** 恶意脚本或配置错误可能导致通知刷屏，影响用户体验和系统稳定性。

**建议：**
在 `tests/integration/local-trigger.test.ts` 中增加速率限制测试用例：
- 正常速率下请求成功
- 超过 `rateLimitPerMinute` 后返回 429
- 等待窗口重置后恢复正常

**优先级：** 中（安全与稳定性）

---

## 二、功能扩展方向（按优先级排序）

### 1. 手机配对与设备管理 MVP

**现状：** `docs/delivery-roadmap.md` 0.3 阶段定义了设备配对，但代码中只有文件传输的 LocalSend 协议实现，没有持久设备身份、配对码或设备列表管理。

**差距：**
- 没有 `DeviceService`
- 没有设备配对流程（二维码 / 配对码）
- 没有设备在线状态心跳
- 传输依赖 LocalSend 临时会话，每次需要重新发现

**建议实现（第一版）：**
1. **设备发现与配对**
   - 电脑生成配对二维码（包含局域网 IP、端口、一次性 token）
   - Android App 扫码后，双方完成密钥交换并保存设备身份
   - 设备记录包含：deviceId、name、platform、publicKey、lastSeen、authorized

2. **设备服务**
   - `packages/platform-services/src/device/service.ts`
   - 提供 `list()`、`pair(token)`、`revoke(deviceId)`、`getStatus(deviceId)` 接口
   - 持久化设备列表到 `PlatformStorage`

3. **连接保活**
   - 已配对设备每 30 秒发一次心跳
   - 更新 `lastSeen` 时间戳
   - 超过 3 分钟未响应标记为 `offline`

4. **工作台设备管理页**
   - `console-apps/workbench/devices.html`
   - 显示已配对设备、在线状态、配对时间
   - 提供撤销授权按钮

5. **官方设备模块**
   - `modules/device-bridge/`
   - Small 态显示"手机已连接"或"未连接"
   - Medium 态显示设备列表与配对入口

**依赖：** Android App 需要同步开发配对扫码与心跳功能。

**验收标准：**
- 配对流程在 1 分钟内完成
- 重启后自动重连
- 断线 30 秒内恢复不触发"离线"提示
- 撤销授权后，该设备无法再次连接（除非重新配对）

**优先级：** 🔥 **最高**（roadmap 0.3，是后续所有跨设备功能的基础）

---

### 2. Android 通知同步

**现状：** Windows 通知已完成，但手机通知同步还未启动。

**前置条件：** 设备配对完成（上一条）。

**建议实现（第一版）：**
1. **Android 端**
   - 申请通知监听权限（NotificationListenerService）
   - 用户选择哪些 App 的通知允许同步（白名单机制）
   - 通知发生时，通过已建立的加密连接发送到电脑
   - 通知结构：appName、title、text、timestamp、actionable（是否可操作）

2. **电脑端**
   - `NotificationService` 增加 `phone` 来源类型
   - 为手机通知生成稳定的 `eventId`（避免电脑和手机重复提醒）
   - 支持手机通知的独立过滤策略（如"仅显示标题"、"静音模式"）

3. **隐私控制**
   - 设置中提供"手机通知"开关
   - 可按应用设置：完全同步 / 仅标题 / 不同步
   - 敏感关键词过滤（如包含"密码"的通知可选隐藏正文）

4. **去重机制**
   - 如果同一通知在手机和电脑都产生（如 Telegram 同时在两端登录），只显示一次
   - 使用 `sourceApp + contentHash + timestamp` 生成去重 ID

**验收标准：**
- 用户能明确选择哪些手机通知类别能到达电脑
- 通知延迟 < 2 秒（局域网环境）
- 手机和电脑重复登录的 App 不会双重提醒
- 隐私过滤可配置且立即生效

**优先级：** 高（roadmap 0.5，核心卖点）

---

### 3. 插件能力声明与权限系统（契约 v3）

**现状：** 插件可以调用所有平台 API，没有细粒度权限控制。`docs/plugin-contract.md` 提到了 `capabilities` 字段，但实际代码中只在 `plugin-view-manager.ts` 里看到 `capabilities: []` 的空数组。

**风险：** 第三方插件可以读取所有通知正文、手机数据和文件传输会话，存在隐私泄露风险。

**建议实现（契约 v3）：**
1. **能力声明**
   - 插件 manifest 增加 `capabilities` 和 `subscriptions` 字段：
     ```json
     {
       "contract": 3,
       "capabilities": [
         "notifications.subscribe:metadata",
         "devices.list",
         "transfers.create"
       ],
       "subscriptions": [
         "transfer.updated"
       ]
     }
     ```

2. **能力级别**
   - `notifications.subscribe:metadata`：只收到应用名、标题和时间（无正文）
   - `notifications.subscribe:content`：收到完整正文（需单独授权）
   - `devices.list`：查看已授权设备列表
   - `devices.connect`：发起连接（需用户确认）
   - `transfers.create`：创建传输会话
   - `transfers.read:own`：查询自己创建的传输
   - `transfers.read:all`：查询所有传输（敏感）

3. **权限审批流程**
   - 插件安装时，显示权限清单
   - 敏感权限（如读取通知正文）需用户单独确认
   - 用户可在设置中按插件查看和撤销权限

4. **运行时检查**
   - `EventRouter` 根据插件声明的 `subscriptions` 过滤事件
   - 平台 API 调用时检查 `capabilities`，未授权则返回 `{ ok: false, error: 'capability-not-granted' }`

5. **向后兼容**
   - v2 插件继续运行，但只能访问低敏感 API
   - v3 插件必须声明能力

**验收标准：**
- v2 插件不受影响
- v3 插件未声明 `notifications.subscribe:content` 时，收到的通知事件中 `content` 字段为空
- 用户可以在设置中撤销插件权限，撤销后插件调用对应 API 返回错误

**优先级：** 高（roadmap 0.6，生态安全基础）

---

### 4. 文件传输增强：断点续传与多任务队列

**现状：** LocalSend 协议支持取消，但中断后需要重新选择文件发送，没有断点续传。

**用户痛点：** 传输大文件时网络闪断、手机锁屏或切换 Wi-Fi 会导致从头开始。

**建议实现：**
1. **会话持久化**
   - 传输会话包含 `sessionId`、`files`、`progress`、`state`（pending/active/paused/completed/failed）
   - 持久化到 `PlatformStorage`，重启后可恢复

2. **分片与校验**
   - 文件按 1MB 分片
   - 每个分片传输后记录校验和（SHA-256）
   - 中断后，接收方告知发送方已收到哪些分片

3. **断点续传**
   - 传输失败后，会话进入 `paused` 状态
   - 用户点击"重试"后，发送方跳过已完成的分片
   - 全部分片到达后，接收方校验完整文件哈希

4. **多任务队列**
   - 支持同时排队多个传输任务
   - 工作台显示队列状态、单个任务可暂停/取消/重试
   - Small 态显示活跃任务进度，Medium 态展开队列列表

**验收标准：**
- 传输 100MB 文件时，中途断网 10 秒，恢复后从断点继续（不重传已完成部分）
- 同时向 3 台设备发送文件，任务依次执行，队列可见
- 重启后，未完成的传输显示在队列中，可手动恢复

**优先级：** 中（体验优化，可在 0.4 完成基础传输后逐步迭代）

---

### 5. 剪贴板同步

**现状：** roadmap 提到剪贴板同步，但代码中未找到相关实现。

**建议实现（第一版）：**
1. **同步策略**
   - 默认关闭，用户在设置中手动开启
   - 支持双向同步：电脑复制 → 手机粘贴，手机复制 → 电脑粘贴
   - 仅同步文本，不同步文件和图片（第二阶段再支持）

2. **冲突处理**
   - 同一设备短时间内多次复制，只发送最后一次
   - 两端同时复制不同内容，以时间戳较新的为准

3. **安全限制**
   - 单次剪贴板内容最大 64KB
   - 敏感关键词检测（如"密码"、"信用卡"），可选不同步
   - 用户可设置"仅在设备配对时同步"（非公共 Wi-Fi）

4. **隐私提示**
   - 首次开启时，明确告知剪贴板内容会传输到手机
   - 提供"临时暂停同步"快捷方式

**验收标准：**
- 电脑复制文本后 < 1 秒在手机上可粘贴
- 包含"密码"的内容触发过滤，不同步（用户可关闭此规则）
- 关闭同步开关后，剪贴板立即停止传输

**优先级：** 中（roadmap 0.7，高频场景但非核心卖点）

### 6. AI 生成插件能力

**现状：** DESIGN.md 提到"配套 Skill 让 AI 生成插件"，但代码中只有插件脚手架（`scripts/new-plugin.mjs`），没有 AI 生成流程。

**建议实现：**
1. **Skill 定义**
   - `apps/desktop/skills/island-plugin/SKILL.md` 已存在（236 行），可能已包含生成逻辑
   - 确保 Skill 能根据用户需求描述生成插件代码（HTML + JS）

2. **生成流程**
   - 用户在工作台或聊天界面描述需求（如"我要一个显示 GitHub 仓库 star 数的插件"）
   - AI 根据需求生成插件代码
   - 预览插件效果（沙盒环境）
   - 用户确认后安装到本地插件目录

3. **安全审查**
   - 生成的插件代码进行静态检查（如禁止 `eval`、限制网络请求域名）
   - 明确告知用户插件声明的能力
   - 提供"查看代码"按钮，技术用户可审查

**验收标准：**
- 用户用自然语言描述需求，AI 生成可运行的插件
- 生成的插件通过安全检查
- 用户可编辑生成的代码后重新安装

**优先级：** 低（差异化功能，但需要手机配对、权限系统等基础能力先完成）

## 五、风险与注意事项

1. **Android 开发同步**：设备配对、通知同步、剪贴板都需要 Android 端配合开发，需要协调资源。

2. **隐私合规**：
   - 手机通知同步涉及敏感数据，需明确告知用户并提供细粒度控制
   - 剪贴板同步可能涉及密码等敏感内容，需要过滤机制
   - 插件权限系统必须在手机通知上线前完成，否则存在隐私泄露风险

3. **向后兼容**：
   - v2 插件需要在 v3 推出后继续可用
   - 数据迁移（如设备列表、通知历史）需要有升级脚本

4. **网络环境限制**：
   - LocalSend 依赖局域网，无法在不同 Wi-Fi 或移动网络下使用
   - 如需支持公网传输，需引入中继服务器（roadmap 暂缓范围）

5. **资源消耗**：
   - 通知监听、设备心跳、剪贴板轮询会持续占用 CPU 和内存
   - 需要优化轮询频率和事件去重，避免影响系统性能

---

## 总结

**立即行动项（下周就能开始）：**
1. 拆分 main.ts（改善代码结构）
2. 统一 platform-services 代码（消除技术债）
3. 补全无障碍支持（提升产品质量）

**核心价值项（未来 1-2 个月）：**
4. 设备配对 MVP（解锁所有跨设备功能）
5. Android 通知同步（核心卖点）
6. 插件权限系统（生态安全基础）

**体验优化项（持续迭代）：**
7. 断点续传、剪贴板同步、AI 生成插件

按这个顺序推进，可以在保持现有功能稳定的前提下，逐步实现从"Windows 灵动岛"到"电脑与手机之间的轻量信息与操作入口"的产品演进。
